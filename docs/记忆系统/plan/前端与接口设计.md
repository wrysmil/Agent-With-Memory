# Nanobot 三层记忆系统 - WebUI 前端与后端 API 设计

> 状态: 🔍 设计稿（调研完成，待评审）
> 适用范围: nanobot 三层记忆系统（情节 / 语义 / 工作记忆）的 WebUI 维护界面与前后端接口
> 前置文档: [`数据库设计.md`](./数据库设计.md)（schema v1 已实现）；三方调研见 `../记忆系统存储三方系统调研.md`
> 本文档回答: 前端如何"维护 / 查看 / 增删改"记忆，后端需要提供哪些接口

---

## 一、目标与范围

### 1.1 目标

在现有 SQLite 存储层（`nanobot/memory/`）之上，为 nanobot WebUI 增加一层**记忆管理能力**，使：
- 用户可以**浏览、搜索、手动新增 / 编辑 / 删除**三层记忆（尤其语义记忆 `memories` 是主要维护对象）
- 可以**查看**情节记忆（`episodes`）与工作记忆（`scratchpad`），并对 scratchpad 进行编辑
- 前端所有读写都通过**后端网关**提供的接口，沿用 nanobot 既定鉴权模式，不另造安全机制

### 1.2 本轮做什么 / 不做什么

| 做                                                               | 不做                                                   |
| ---------------------------------------------------------------- | ------------------------------------------------------ |
| 后端：新增 WebUI 域的 memory 读写接口（HTTP 读取 + WebSocket mutation） | 不接 Dream / Consolidator 写入路径（下轮再设计）             |
| 后端：补齐 repository 缺失的 CRUD（`update_memory` 等）         | 不改 `history.jsonl` / `MEMORY.md` / `SOUL.md` / `USER.md` |
| 前端：新增设置页"记忆"管理与维护界面                            | 不做向量检索 / Embedding 界面                          |
| 前端：语义记忆列表 + 搜索 + 增删改、情节列表、工作便签编辑      | 不做记忆"自动提取"的前端编排（仍是后端下轮的事）           |

> 关键不变：与 `数据库设计.md` 一致，`MEMORY.md / SOUL.md / USER.md` 仍是**直接注入 LLM 上下文**的 Markdown 视图；本功能操作的是 **SQLite 结构化检索层**，两者独立、不强制同步。前端界面维护的是 SQLite 里的结构化记忆条目。

## 二、现状调研（结论）

### 2.1 后端存储层已具备的能力（`nanobot/memory/`）

| 模块              | 能力                                                                                            |
| ----------------- | ----------------------------------------------------------------------------------------------- |
| `database.py`   | `MemoryDatabase(workspace)` → `connect()` 串行连接；`init_schema()`；DB 位置 `workspace/memory/state.db` |
| `models.py`     | `Memory` / `Episode` / `ScratchpadEntry` dataclass + 枚举（`MemoryType`…）                     |
| `repository.py`  | `add_memory / get_memory / list_memories / search_memories / delete_memory`；`add_episode / get_episode / list_episodes_by_session`；`upsert_scratchpad / get_scratchpad` |

**调研发现的缺口（本轮后端需补齐）**：

| 缺失能力                  | 现状                                         | 影响                                       |
| ------------------------- | -------------------------------------------- | ------------------------------------------ |
| `update_memory`          | **没有** `UPDATE` 语句，只有 insert/delete    | 前端"编辑记忆"无法落地                     |
| `update_episode`         | **没有**                                      | 前端编辑情节摘要/标签无法落地               |
| `delete_episode`         | **没有**                                      | 前端删除情节                                  |
| `list_episodes`（全量）  | 只有 `list_episodes_by_session`             | 前端"最近任务"列表无法覆盖跨会话            |
| （记忆计数 / 统计）      | 无聚合查询                                   | 前端概览卡片如需计数需新增                  |

> 说明：`memories` 既有 FTS5 触发器中 `AFTER UPDATE` 已做 delete+reinsert，故补充 `update_memory` 后全文索引自动保持一致，无需改触发器。

### 2.2 WebUI 前后端通信机制（已有，需沿用）

nanobot 的 WebUI 读写走 gateway 的 WebSocket 复用通道，分两类：

1. **读取（HTTP GET / POST）**：`webui/src/lib/api.ts` 的 `request<T>(url, token, ...)`（带 `Authorization: Bearer <token>`）→ gateway `nanobot/webui/ws_http.py` 的 `WsHttpDispatch.dispatch()` → 按前缀分发到各域 router（settings / session / media / misc…）。
2. **变更（WebSocket mutation）**：`webui/src/lib/nanobot-client.ts` 的 `client.requestMutation<T>(action, args)` → gateway `dispatch_webui_mutation()` → 经 `_WEBUI_MUTATION_PATHS` action→path 映射 → 复用同一批 router 处理。mutation 在结构上强制 `_is_webui_mutation_path()` 白名单，未授权 WebSocket 一律 405。

**本设计遵循这个既有二分**：读取用 HTTP GET 路由，写操作走 mutation action，与现有 skills / automations / settings 保持一致，前端零新协议。

### 2.3 后端如何拿到记忆库实例

- 工作区路径：`nanobot/config/paths.py::get_workspace_path(workspace)`；配置侧 `config.workspace_path` 给出当前工作区。
- 记忆库：`MemoryDatabase(get_workspace_path(...))`，DB 落到 `workspace/memory/state.db`，与 `数据库设计.md` 一致。
- gateway 已在网关进程内持有一份配置，可在该进程内惰性构造并复用同一 `MemoryDatabase` 实例（避免每次请求连库）。

## 三、后端接口设计

### 3.1 总体结构

新增一个 WebUI 域模块 `nanobot/webui/memory_api.py`（仿 `skills_api.py`：纯 payload/action 函数，不含 transport 逻辑），并把它接到 gateway 的 HTTP 读取分发与 mutation 路径表。读取与变更均由 gateway 统一鉴权（Bearer token），不另置权限。

```
WebUI (browser)
  │ HTTP GET /api/settings/memory/...   (读取)
  │ client.requestMutation("memory.*", args)   (写)
  ▼
gateway: ws_http.py
   ├── _dispatch_resolved()  → 新增分支 → memory_api.read_*()
   └── dispatch_webui_mutation() → _WEBUI_MUTATION_PATHS → memory_api.memory_*()
  ▼
nanobot/memory/repository.py   (CRUD + FTS5)
```

### 3.2 读取接口（HTTP GET，均需 Bearer token）

统一前缀 `/api/settings/memory`（挂在 WebUISettingsRouter 的 settings 域下，复用其读/写两套分派与 Bearer 鉴权），全部返回 JSON。

| 方法与路径                                                        | 说明                          | 响应（examples）                                             |
| ----------------------------------------------------------------- | ----------------------------- | ------------------------------------------------------------ |
| `GET /api/settings/memory/memories`                             | 列出语义记忆                 | `{ "items": [ MemoryPayload ] }`                           |
| `GET /api/settings/memory/memories/{id}`                        | 查单条                        | `{ memory: MemoryPayload }` 或 404                          |
| `GET /api/settings/memory/memories/search?q=关键词`             | FTS5 全文检索（BM25+重要度） | `{ items, query }`                                         |
| `GET /api/settings/memory/episodes`                             | 列出情节（可按 session）      | `{ items: [ EpisodePayload ] }`                           |
| `GET /api/settings/memory/episodes/{id}`                        | 查单条情节                     | `{ episode: EpisodePayload }` 或 404                       |
| `GET /api/settings/memory/scratchpad`                           | 读工作便签（当前 workspace）   | `{ scratchpad: ScratchpadPayload \| null }`               |
| `GET /api/settings/memory/stats`                                | 汇总（各类型计数、总条数）  | `{ total, by_type: {...} }`（用于页面前览卡）             |

查询参数（可在这两个路径复用）：`type`、`priority`、`order`（`created`/`importance`）、`limit`、`workspace_id`（默认当前 workspace）。

**列表/搜索的页面化**：v1 返回为简单整形 `pagesize` 参数可选；若后续量大再引入游标分页（见 §7）。

### 3.3 Mutation 接口（WebSocket `requestMutation`）

| action          | 参数（payload）                                             | 行为                 | 返回 |
| --------------- | ----------------------------------------------------------- | -------------------- | ---- |
| `memory.create` | `{ id?, content, type, priority, tags, subject?, predicate?, importance_score?, metadata? }` | 新增记忆 | `{ memory }` |
| `memory.update` | `{ id, content?, type?, ... }`                              | 更新记忆（触发 FTS 同步） | `{ memory }` |
| `memory.delete` | `{ id }`                                                    | 删除记忆            | `{ ok: true }` |
| `episode.delete`| `{ id }`                                                    | 删除情节            | `{ ok: true }` |
| `scratchpad.save` | `{ content?, active_projects?, current_focus?, open_questions?, next_steps? }` | UPSERT 工作手记 | `{ scratchpad }` |

> mutation 的 payload 会经 `dispatch_webui_mutation()` 装载为 `_WEBUI_MUTATION_PAYLOAD_ATTR`，路由侧读取；**只允许显式白名单 action**，未知 action 一律 404。前端 `action` 名与后端 `_WEBUI_MUTATION_PATHS` 键一一对应。

### 3.4 数据契约（JSON payload）

后端把 dataclass 转成 JSON 兼容结构，**JSON 列反序列化为数组/对象**（不复用 `to_row()` 的字符串形式）：

```
MemoryPayload =
  { id, content, type, priority, source,                      # source: manual/extraction/consolidation
    importance_score, access_count,
    tags: string[], subject, predicate, confidence,
    expires_at?, last_accessed_at?,
    superseded_by?, source_episode_id?,
    scope, workspace_id, created_at, updated_at,
    metadata: object }
EpisodePayload =
  { id, session_id, summary, goal, outcome, source,
    started_at, ended_at,
    action_nodes: object[], entities: string[], tools_used: string[],
    linked_memory_ids: string[], tags: string[],
    importance_score, },
ScratchpadPayload =
  { user_id, workspace_id, content, active_projects: string[],
    current_focus, open_questions: string[], next_steps: string[], updated_at }
```

建议在 `memory_api.py` 提供 `model_to_payload(model)` 系列转换函数（`Memory`→`MemoryPayload` 等），保持 Repository 层与 wire 层职责分离。

### 3.5 后端接线改动清单

| 文件 | 改动 |
| ------------------------------------------ | ------------------------------------------------------------ |
| `nanobot/webui/memory_api.py`（新增）        | 定义 payload 转换 + read 处理函数（list/search/get/episodes/scratchpad/stats）+ mutation 处理函数（create/update/delete/save），均以 `MemoryServices`（含 `MemoryDatabase` 访问器）为依赖 |
| `nanobot/webui/settings_services.py`（或新 `webui/memory_services.py`） | 提供 `MemoryServices`：惰性 `memory_db()`（`MemoryDatabase(get_workspace_path(config.workspace_path))`），保证 `ensure_schema()` |
| `nanobot/webui/settings_routes.py`（`WebUISettingsRouter` + `ws_http` 接线） | 在 settings 域路由表加 `/api/settings/memory/...`（read 组）+ mutation 组；mutation action 加入 `_WEBUI_MUTATION_PATHS` + `_is_webui_mutation_path` 白名单 |
| `nanobot/memory/repository.py`   | 补 `update_memory / update_episode / delete_episode / list_episodes(all)`、可选 `memory_stats` |

> **位置定案**：memory 属"设置/管理"性质，**统一挂在 `settings` 域之下**（读写前缀 `/api/settings/memory/...`；mutation action→path 也落在 `/api/settings/memory/...`）。这样直接复用 `WebUISettingsRouter` 的 `domain`/`action` 分派与 Bearer 鉴权装饰，与前例 `skills_api.py` 同层级；**不再保留独立的 `/api/memory` 前缀路线**，避免两套路由并存。mutation action 名仍为 `memory.create / episode.delete / scratchpad.save`，仅其映射目标统一到 settings 域。

## 四、前端设计

### 4.1 入口与导航

记忆维护是一个**独立分域**，最贴合现有结构的是在 **Settings 新增「记忆」分区**（`SettingsSectionKey` 增加 `"memory"`），与 `skills / automations` 同级：

- [webui/src/components/settings/contracts.ts](webui/src/components/settings/contracts.ts)：`SettingsSectionKey` 增加 `"memory"`。
- `WebUISettingsSidebar` / 分区布局：增加「记忆」卡片，点击切换到记忆域界面。
- 一处 `App.tsx`/路由按需注册（与 skills 一致）。

> 备选：做成独立的 `Memor/MemoryManagePage` 顶层视图。但 Settings 分区已集成导航/侧栏/主题/鉴权，改动最小、体验一致，故优先 Settings 方案。

### 4.2 页面与组件

记忆域内部建议拆为 3 个子视图（用一个内部 Tab 切换）：

| 视图            | 组件（新）                                          | 职责 |
| --------------- | --------------------------------------------------- | ------------------------------------------------------------ |
| 语义记忆        | `MemoryListView.tsx` / `MemoryCard.tsx` / `MemoryEditDialog.tsx`（或 `MemoryEditor.tsx`） | 列表 + 类型过滤 + 关键词搜索 + 新建/编辑/删除 + 详情查看 |
| 情节记忆        | `EpisodeListView.tsx` / `EpisodeDetailPanel.tsx`     | 只看/各会话条目、展开详情可视化 action_nodes / tools_used，支持删除 |
| 工作记忆        | `ScratchpadEditor.tsx`                               | 编辑 `content`（Markdown 预览）、`active_projects`、`current_focus`、`open_questions`、`next_steps`，保存 |

### 4.3 前端读取 / 变更封装

- **Types**：在 [webui/src/lib/types.ts](webui/src/lib/types.ts) 增加 `MemoryPayload` / `EpisodePayload` / `ScratchpadPayload` 及枚举字符串联合（`MemoryType`/`MemoryPriority`/`EpisodeOutcome`）。
- **读取**：在 [webui/src/lib/api.ts](webui/src/lib/api.ts) 仿现有函数新增：
  - `listMemories(token, base, opts)` → `GET /api/settings/memory/memories`
  - `searchMemories(token, base, q, opts)` → `/search`
  - `fetchMemory(token, base, id)` / `fetchEpisode` / `fetchScratchpad` / `fetchMemoryStats`
- **变更**：通过 `useClient()` 提供的 `client.requestMutation<Resp>(action, args)`（见 `skills` 一次写流量），封装：
  - `createMemory(...)` / `updateMemory(...)` / `deleteMemory(...)` → `memory.create/update/delete`
  - `saveScratchpad(...)` → `scratchpad.save`
- 组件统一在 `useClient()` 取 `{ client, token }`（与现有 settings 页一致，[useSettingsController.ts](webui/src/components/settings/useSettingsController.ts) 已验证）。

### 4.4 交互细节（合理默认）

- **新建默认值**：`type=fact, priority=long_term, importance_score=0.5, tags=[]`，与后端默认一致，减少用户负担。
- **搜索**：输入防抖（~300ms）+ `q` 空则回退到列表。
- **编辑**：仅允许改 `content / type / tags / subject / predicate / scope / importance_score / priority`，`id / created_at / workspace_id` 只读。
- **删除**：二次确认（DeleteConfirm 组件已有）。
- **安全**：全部接口只走 gateway，读取用 Bearer token，mutation 走已鉴权 WS；前端不在 URL 或 JS 中放任何可写内存数据（避免 XSS 注入 memory_content 渲染，统一用 MarkdownText 渲染）。

## 五、数据串流示例（一条检索）

```
User 词汇 "午餐偏好" 搜索
  → webui: searchMemories(token, "/api/settings/memory/memories/search?q=午餐偏好")
  → gateway: FTS5 MATCH + BM25 rank, importance 加权
  → JSON: { items: [ MemoryPayload ] }
  → webui: MemoryCard 渲染 → 点击 → fetchMemory(id) → 详情
```

## 六、安全与边界

- 读接口依赖 `check_api_token`（Bearer），写 mutation 依赖已鉴权 WebSocket；无外网暴露风险（与现有 settings/skills 一致）。
- `content` 等用户输入按 React 默认转义；渲染 markdown 用现有 `MarkdownText`（已 HTML 清理）。
- `workspace_id` 由服务端用当前 workspace 注入，前端不可越权指定其它 workspace。

## 七、开放问题（实施前确认）

1. **分页形态**：数据量小先用一次性 `limit` 解析；若需要正式分页，改为游标（`updated_at DESC` + last_id）。请在评审中定夺。
2. **「记忆」入口位置**：放 Settings 分区 vs 独立顶层页，见 4.1。
3. **手动新增记忆的 `source` 取值**：设为 `manual`（默认），前端是否暴露 `extraction/consolidation` 选择（用户手动补过往提取缺失的）。
4. **是否需要**只读的"记忆只读（仅列表、禁止编辑）"权限开关，应用于只读网关。
