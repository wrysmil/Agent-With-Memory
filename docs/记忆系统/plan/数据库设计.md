# Nanobot 三层记忆系统 - 数据库设计文档

> 状态: ✅ 已实现（schema v1）
> 适用范围: nanobot 三层记忆系统（情节 / 语义 / 工作记忆）的 SQLite 存储层
> 与三方调研文档的关系: 精简版实现。完整字段定义见 `记忆系统存储三方系统调研.md`；本文档标注精简与差异理由。

---

## 一、设计目标

### 1.1 总目标

为 nanobot 引入结构化的三层记忆存储，使 Agent 能够在会话内、会话间、跨会话三个时间尺度上，保留"事实/故事/便签"三类语义不同的记忆单元，并支持全文检索。

### 1.2 设计原则

| 原则                                | 含义                                                                                                                                                                                                                  |
| ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **语义分层**                  | 事实（Semantic）、故事（Episode）、便签（Scratchpad）三类记忆用独立表存储，不允许跨类型合并存储                                                                                                                       |
| **存储与编码分离**            | 表结构只关心"如何持久化"，不规定"LLM 怎么写"；写入路径后续单独设计                                                                                                                                                    |
| **不破坏现有体系**            | 不替换`history.jsonl` / `MEMORY.md` / `SOUL.md` / `USER.md`；不修改 Dream 流程                                                                                                                                |
| **Markdown 与 SQLite 双视图** | `MEMORY.md` / `SOUL.md` / `USER.md` 是**直接注入到 LLM 上下文**的可读视图（已被现有 Agent 链路消费），SQLite 是**结构化检索层**（用于事实检索、权重排序、跨字段过滤）；两者独立维护，不需要严格同步 |
| **最小可行**                  | 首版仅交付 3 张核心表 + FTS5，不做迁移脚本、不接写入路径                                                                                                                                                              |
| **兼容 nanobot 现状**         | 复用 workspace 隔离机制，暂不引入多用户多租户场景                                                                                                                                                                     |
| **可演进**                    | schema 引入版本号，预留升级路径；FTS5 仅覆盖语义记忆                                                                                                                                                                  |

### 1.3 本设计不做什么（明确范围）

| 不在本轮范围                                               | 原因                                              |
| ---------------------------------------------------------- | ------------------------------------------------- |
| 一次性迁移脚本                                             | 用户明确要求延后；当前数据量小，按需手动迁移即可  |
| 接入 Consolidator / Dream 写入路径                         | 用户选择"Dream 完全不动"；写入路径下轮再设计      |
| 向量检索 / Embedding                                       | 暂不引入外部依赖；先用 FTS5 + BM25 满足检索需求   |
| 附件表（`attachments`）                                  | 当前场景无多媒体需求，后续按需扩展                |
| 多用户多租户（`user_id` 多值、`session_tenants` 映射） | nanobot 现状为单 agent 单用户，预留字段但不强约束 |
| 知识图谱（SPO 边表、关系推理）                             | OpenAkita 的 MDRM 暂不引入                        |

## 二、三层记忆模型与表映射

### 2.1 概念模型

| 层级                  | 类比       | 用途                                           | 生命周期                                   | 表             |
| --------------------- | ---------- | ---------------------------------------------- | ------------------------------------------ | -------------- |
| 语义记忆 (Semantic)   | 知识笔记本 | 事实、偏好、规则、技能、错误教训、可复用经验   | 长期（`priority` + `expires_at` 控制） | `memories`   |
| 情节记忆 (Episode)    | 日记       | 完整任务故事、工具调用链、决策上下文           | 半长期（按`outcome` 决定保留期）         | `episodes`   |
| 工作记忆 (Scratchpad) | 办公桌便签 | 当前任务状态、活跃项目、待解决问题、下一步计划 | 跨会话保留，主动更新                       | `scratchpad` |

### 2.2 与现有 nanobot 体系的对应关系

nanobot 现有"记忆"主要由**文件 + Markdown**承担，与新 SQLite 表并存：

| 现有文件                                  | 角色                                                                     | 本轮关系                                                                     |
| ----------------------------------------- | ------------------------------------------------------------------------ | ---------------------------------------------------------------------------- |
| `session.messages` (JSONL)              | 实时对话流                                                               | 不替换；作为情节记忆的原始素材源                                             |
| `memory/history.jsonl`                  | Consolidator 产出的追加历史                                              | 不替换；下轮接入 Consolidator 时，将其转化为`memories` / `episodes` 写入 |
| `SOUL.md` / `USER.md` / `MEMORY.md` | **直接注入 LLM 上下文**的 Markdown 知识（已被现有 Agent 链路消费） | 保持 Markdown 原貌不动；本轮不导出、不解析、不修改                           |
| GitStore                                  | 知识文件版本审计                                                         | 不替换；保留`/dream-log` / `/dream-restore`                              |

**双视图关系**：Markdown 文件保留为"上下文注入视图"（这是 nanobot 既定的 Agent 消费方式），SQLite 是新增的"结构化检索层"。两者**独立维护**，不要求严格同步：

- Markdown 继续由 Dream 整合 + 用户编辑；它是给 LLM 看的可读知识
- SQLite 由未来的 Consolidator/提取器写入；它是给 Agent 检索的结构化事实
- 本轮仅交付 SQLite 存储层，不接任何写入路径；Markdown 与 SQLite 之间没有任何耦合

## 三、存储介质与位置

### 3.1 介质: SQLite 3 + FTS5

- 理由: nanobot 已在 `nanobot/llm_usage/store.py` 使用 `sqlite3`，无新增依赖
- FTS5: 内置于 Python 3.11+ 自带 `sqlite3` 模块（编译选项默认开启），无需额外安装
- 同步模型: 同步 API + `threading.Lock` 串行化（与 `llm_usage/store.py` 一致），不引入异步层
- **Markdown 文件保留**: `MEMORY.md` / `SOUL.md` / `USER.md` 不被 SQLite 替换或派生，仍是注入上下文的载体

### 3.2 物理位置: `workspace/memory/state.db`

- 与 `MEMORY.md` / `history.jsonl` 同目录
- 与 `session.messages`（位于运行时根目录）严格区分；后者是"会话临时态"，前者是"知识持久态"
- workspace 切换即知识隔离（符合 nanobot 现状）

### 3.3 标识符

- `workspace_id`: 默认 `'default'`，由调用方从 `nanobot.config` 注入
- `user_id`: 默认 `'default'`，预留多用户扩展
- `agent_id`: 默认 `''`，预留多 agent 扩展
- `scope`: `global` / `user` / `session` / `pending_consolidation` / `legacy_quarantine`，默认 `global`

### 3.4 Markdown 文件保留策略

`SOUL.md` / `USER.md` / `MEMORY.md` 在 nanobot 中是**直接注入到 LLM 上下文**的知识载体（见 `nanobot/agent/memory.py` 中的 `read_memory()` / `read_soul()` / `read_user()`），它们给 LLM 提供了：

- 一致的"自我风格"（`SOUL.md`）
- 用户偏好画像（`USER.md`）
- 项目级长期事实（`MEMORY.md`）

这种"Markdown 直注"是 nanobot 既定的 Agent 链路，**本设计完全保留**：

- ✅ Markdown 文件位置不动，仍在 `workspace/` 根目录（`SOUL.md` / `USER.md`）和 `workspace/memory/`（`MEMORY.md`）
- ✅ Markdown 内容由 Dream 整合 + 用户手动维护，**不依赖** SQLite 表
- ✅ SQLite 表与 Markdown 之间**不**做任何同步、解析、派生
- ✅ `/dream-log` / `/dream-restore` 等 git 审计链路完全不受 SQLite 引入的影响
- ⏸ SQLite 表的写入路径（Consolidator 提取 / Dream 派生）下轮设计；届时也只是"另外写一份"，不会"取代 Markdown"

**结论**：SQLite 是结构化检索层（用于 `search_memory` 等工具按类型/权重/关键词检索），Markdown 是上下文注入层（用于每次对话的 system prompt 直注）。两者职责不同，并存而非替代。

## 四、表结构设计

### 4.1 `memories`（语义记忆表）

> 存储偏好、事实、规则、经验等可独立引用的知识单元。

```sql
CREATE TABLE IF NOT EXISTS memories (
    id              TEXT    PRIMARY KEY,        -- UUID4 字符串
    content         TEXT    NOT NULL,           -- 记忆正文（LLM 可阅读）
    type            TEXT    NOT NULL DEFAULT 'fact',
                                              -- fact / preference / skill / error / rule / experience
    priority        TEXT    NOT NULL DEFAULT 'long_term',
                                              -- short_term / long_term
    source          TEXT    NOT NULL DEFAULT 'manual',
                                              -- manual / extraction / consolidation
    importance_score REAL   NOT NULL DEFAULT 0.5,    -- 0.0-1.0
    access_count    INTEGER NOT NULL DEFAULT 0,
    tags            TEXT    NOT NULL DEFAULT '[]',    -- JSON array
    subject         TEXT    NOT NULL DEFAULT '',      -- SPO 三元组主语
    predicate       TEXT    NOT NULL DEFAULT '',      -- SPO 三元组谓词
    confidence      REAL    NOT NULL DEFAULT 0.5,     -- 0.0-1.0
    decay_rate      REAL    NOT NULL DEFAULT 0.1,     -- 重要性衰减率
    expires_at      TEXT,                            -- ISO8601；NULL = 不过期
    last_accessed_at TEXT,                           -- ISO8601
    superseded_by   TEXT,                            -- FK→memories.id
    source_episode_id TEXT,                          -- FK→episodes.id
    scope           TEXT    NOT NULL DEFAULT 'global',
    scope_owner     TEXT    NOT NULL DEFAULT '',
    agent_id        TEXT    NOT NULL DEFAULT '',
    user_id         TEXT    NOT NULL DEFAULT 'default',
    workspace_id    TEXT    NOT NULL DEFAULT 'default',
    metadata        TEXT    NOT NULL DEFAULT '{}',   -- JSON object
    created_at      TEXT    NOT NULL,                 -- ISO8601
    updated_at      TEXT    NOT NULL,                 -- ISO8601

    FOREIGN KEY (superseded_by)    REFERENCES memories(id),
    FOREIGN KEY (source_episode_id) REFERENCES episodes(id)
);

CREATE INDEX IF NOT EXISTS idx_memories_owner
    ON memories(workspace_id, user_id, scope, scope_owner);
CREATE INDEX IF NOT EXISTS idx_memories_type     ON memories(type);
CREATE INDEX IF NOT EXISTS idx_memories_importance
    ON memories(importance_score DESC);
CREATE INDEX IF NOT EXISTS idx_memories_created  ON memories(created_at DESC);
CREATE INDEX IF NOT EXISTS idx_memories_episode  ON memories(source_episode_id);
CREATE INDEX IF NOT EXISTS idx_memories_super    ON memories(superseded_by);
```

**字段精简说明（vs 三方调研）**：

- 保留全部语义字段；调研文档中的 `last_active_at` 已在 nanobot 体系中等价为 `updated_at`，不重复
- `priority` 与 `expires_at` 同时存在：`priority` 是策略标签，`expires_at` 是具体到期时间（用于短期临时记忆）
- `scope` / `scope_owner` 与 `user_id` / `workspace_id` 双层：`scope` 控制可见性（语义层），`user_id` / `workspace_id` 是硬隔离（物理层）

### 4.2 `episodes`（情节记忆表）

> 存储会话任务摘要、工具调用链、决策上下文。

```sql
CREATE TABLE IF NOT EXISTS episodes (
    id          TEXT    PRIMARY KEY,            -- UUID4 字符串
    session_id  TEXT    NOT NULL,                -- 来源会话 key
    summary     TEXT    NOT NULL,                -- LLM 生成的情节摘要
    goal        TEXT    NOT NULL DEFAULT '',     -- 任务目标
    outcome     TEXT    NOT NULL DEFAULT 'completed',
                                                -- completed / failed / partial
    source      TEXT    NOT NULL DEFAULT 'session_end',
                                                -- session_end / context_compress / daily_consolidation
    started_at  TEXT    NOT NULL,                -- ISO8601
    ended_at    TEXT    NOT NULL,                -- ISO8601
    action_nodes       TEXT NOT NULL DEFAULT '[]',  -- JSON array
    entities           TEXT NOT NULL DEFAULT '[]',  -- JSON array
    tools_used         TEXT NOT NULL DEFAULT '[]',  -- JSON array
    linked_memory_ids  TEXT NOT NULL DEFAULT '[]',  -- JSON array of memories.id
    tags               TEXT NOT NULL DEFAULT '[]',  -- JSON array
    importance_score   REAL NOT NULL DEFAULT 0.5,
    access_count       INTEGER NOT NULL DEFAULT 0,
    compaction_checkpoint_id TEXT NOT NULL DEFAULT '',
                                                -- 关联 nanobot 压缩检查点
    workspace_snapshot_id   TEXT NOT NULL DEFAULT ''
                                                -- 关联 nanobot 工作区快照
);

CREATE INDEX IF NOT EXISTS idx_episodes_session ON episodes(session_id);
CREATE INDEX IF NOT EXISTS idx_episodes_time    ON episodes(started_at DESC);
CREATE INDEX IF NOT EXISTS idx_episodes_outcome ON episodes(outcome);
CREATE INDEX IF NOT EXISTS idx_episodes_importance
    ON episodes(importance_score DESC);
```

**字段精简说明**：

- 删除 `session_tenants` 关联：nanobot 已有 workspace_id 物理隔离，不需要外键
- `compaction_checkpoint_id` / `workspace_snapshot_id` 字符串字段，预留对接 nanobot 现有机制（`session.last_consolidated` / `GitStore`），但不强制外键（保留跨系统松耦合）

### 4.3 `scratchpad`（工作记忆表）

> 每用户每工作区一条的工作便签；高频读写，整体替换语义。

```sql
CREATE TABLE IF NOT EXISTS scratchpad (
    user_id         TEXT    NOT NULL,
    workspace_id    TEXT    NOT NULL,
    content         TEXT    NOT NULL DEFAULT '',     -- Markdown 自由内容
    active_projects TEXT    NOT NULL DEFAULT '[]',   -- JSON array
    current_focus   TEXT    NOT NULL DEFAULT '',
    open_questions  TEXT    NOT NULL DEFAULT '[]',   -- JSON array
    next_steps      TEXT    NOT NULL DEFAULT '[]',   -- JSON array
    updated_at      TEXT    NOT NULL,                 -- ISO8601

    PRIMARY KEY (user_id, workspace_id)
);
```

**设计差异说明（vs 三方调研）**：

- 三方文档用 `(user_id)` 单字段作主键；本设计用 `(user_id, workspace_id)` 复合主键，与 nanobot 的 workspace 隔离机制对齐
- nanobot 现状为单 agent 单用户；`user_id` 默认 `'default'`，但保留字段以备未来多用户扩展

## 五、FTS5 全文索引

### 5.1 索引范围

仅对 `memories` 表建立全文索引。理由：`memories` 是用户/Agent 主动检索的主要对象；`episodes` 通过 `summary` 字段可后续单独建索引；`scratchpad` 是高频整体替换的内容，全文检索需求弱。

### 5.2 schema

```sql
CREATE VIRTUAL TABLE IF NOT EXISTS memories_fts USING fts5(
    content,
    subject,
    predicate,
    tags,
    content='memories',
    content_rowid='rowid',
    tokenize='unicode61 remove_diacritics 2'
);
```

**说明**：

- `content='memories'`：启用外部内容模式（外部表删除/更新时同步重建索引）
- `tokenize='unicode61 remove_diacritics 2'`：Unicode 友好分词 + 去音标，适配中英文混合场景
- 关联键：FTS5 通过隐式 `rowid` 与 `memories.rowid` 绑定（SQLite 任何表都有隐式 rowid）

### 5.3 同步触发

需要实现三个 SQLite 触发器保证索引与数据一致：

```sql
CREATE TRIGGER IF NOT EXISTS memories_ai AFTER INSERT ON memories BEGIN
    INSERT INTO memories_fts(rowid, content, subject, predicate, tags)
    VALUES (new.rowid, new.content, new.subject, new.predicate, new.tags);
END;

CREATE TRIGGER IF NOT EXISTS memories_ad AFTER DELETE ON memories BEGIN
    INSERT INTO memories_fts(memories_fts, rowid, content, subject, predicate, tags)
    VALUES ('delete', old.rowid, old.content, old.subject, old.predicate, old.tags);
END;

CREATE TRIGGER IF NOT EXISTS memories_au AFTER UPDATE ON memories BEGIN
    INSERT INTO memories_fts(memories_fts, rowid, content, subject, predicate, tags)
    VALUES ('delete', old.rowid, old.content, old.subject, old.predicate, old.tags);
    INSERT INTO memories_fts(rowid, content, subject, predicate, tags)
    VALUES (new.rowid, new.content, new.subject, new.predicate, new.tags);
END;
```

### 5.4 检索接口

```sql
-- 基础 FTS5 检索
SELECT m.*
FROM memories m
JOIN memories_fts f ON f.rowid = m.rowid
WHERE memories_fts MATCH ?
ORDER BY rank;
```

`rank` 由 FTS5 内置 BM25 算法计算。后续可叠加 `importance_score DESC` 作为加权排序。

## 七、Schema 版本演进策略

### 7.1 版本元数据表

```sql
CREATE TABLE IF NOT EXISTS _schema_meta (
    key   TEXT PRIMARY KEY,
    value TEXT NOT NULL
);
```

应用启动时通过 `SELECT value FROM _schema_meta WHERE key='version'` 获取当前 schema 版本；执行 `_init_schema()` 时按需执行增量迁移。

### 7.2 版本号策略

- 单调递增整数，从 `1` 开始
- 当前设计版本：`1`
- 后续修改表的字段、索引、外键约束时：版本号 +1，并新增对应的 `_migrate_to_N()` 函数
- 不修改表结构的功能性变更（仅修改默认值）：不升级版本号

### 7.3 迁移路径

本轮（v1）创建：

- `memories` / `episodes` / `scratchpad` 三张基础表
- `memories_fts` 虚拟表 + 3 个同步触发器
- `_schema_meta` 版本元数据表

下轮（v2+）预留：

- 增加 `attachments` 表（多媒体场景）
- 增加 `embedding_cache` 表（接入向量检索）
- `episodes.summary` 上 FTS5 索引（如检索需求出现）
