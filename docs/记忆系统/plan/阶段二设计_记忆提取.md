## 一、本阶段目标与非目标

### 1.1 目标

| 目标                                                                                             | 验收标准                                                       |
| ------------------------------------------------------------------------------------------------ | -------------------------------------------------------------- |
| **G1**：在 nanobot Agent 生命周期中，自动把对话内容提取为 memories / episodes / scratchpad | 给定一段对话 → 写出 SQLite 表可查的记录                       |
| **G2**：实现"系统规则 + LLM"双轨混合提取                                                   | 系统能捕获的不调 LLM（ActionNode、规则信号）；语义提取才调 LLM |
| **G3**：防污染：挡住一次性任务伪装成长期记忆                                               | "用户希望生成苹果照片" → 不进 memories 表                     |
| **G4**：去重：同一条记忆不重复入库；相似记忆合并                                           | 重复/高度相似内容 → 自动 skip 或合并                          |
| **G5**：不破坏现有 nanobot 测试                                                            | `pytest tests/` 既有 60+ memory 测试 + 所有 agent 测试全绿   |

### 1.2 非目标（明确不在本阶段范围）

| 非目标                                                                | 理由                                                                                                  |
| --------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| **Topic Change 检测**                                       | 全通道 ≥ 4 轮触发；fire-and-forget 异步提取；详见 §二.2 T5 | OpenAkita 限定 IM，本阶段放开到 CLI/Desktop/WebUI/IM |
| **向量检索 / Embedding**                                        | 数据库设计已预留`embedding_cache` 表空间，Phase 2 不引入新依赖                                      |
| **附件 / 多媒体记忆**                                           | 数据库设计已预留`attachments` 表空间，nanobot 现状无多媒体需求                                      |
| **自动驱动 scratchpad 的 LLM 深度格式化**                       | scratchpad 当前的"系统提取 + 实时同步"已足够；会话结束时再让 LLM 重组是锦上添花，Phase 3 再做         |
| **修改 Markdown 链路**（Dream / MEMORY.md / SOUL.md / USER.md） | Markdown 是 LLM 上下文注入视图；SQLite 是结构化检索视图——**两者独立维护**，见数据库设计 §3.4 |
| **替换现有 MemoryStore**                                        | `nanobot/agent/memory.py` 的 `MemoryStore` 是文件 I/O 层，继续负责 MEMORY.md / history.jsonl      |

### 1.3 与既有体系的边界

```
┌──────────────────────────────────────────────────────────────────┐
│  Markdown 链路 (本阶段不动)                                         │
│  MemoryStore → MEMORY.md / SOUL.md / USER.md / history.jsonl      │
│  Dream → 自动编辑 Markdown + GitStore 审计                         │
│  作用：LLM 上下文注入 + 用户可读                                     │
└──────────────────────────────────────────────────────────────────┘
                          ↕ 完全独立 ↕
┌──────────────────────────────────────────────────────────────────┐
│  SQLite 链路 (Phase 1 存储层 + Phase 2 写入路径)                    │
│  MemoryDatabase → memories / episodes / scratchpad + FTS5         │
│  MemoryExtractor → 自动从 session.messages 提取 → 写入 SQLite       │
│  作用：结构化检索 (search_memory 工具、按类型/权重排序、跨字段过滤)    │
└──────────────────────────────────────────────────────────────────┘
```

**核心约束**：Phase 2 **不读** Markdown 来反向同步 SQLite；**不写** Markdown 来"同步 SQLite 状态"。两条链路只在"用户提问时各自被读取"这个汇聚点上相遇（这是未来检索层的设计，本阶段不涉及）。

## 二、触发时机设计

### 2.1 OpenAkita 触发点对照

根据 [`../记忆提取.md`](../记忆提取.md) §七，OpenAkita 有 7 个触发点：

| 记忆类型       | OpenAkita 触发点                    | nanobot 对应能力                                              |
| -------------- | ----------------------------------- | ------------------------------------------------------------- |
| Scratchpad     | ① 意图分析后即时同步               | ✅ **本阶段做**（每轮消息后系统直写 current_focus）    |
| Scratchpad     | ② 会话结束 LLM 深度格式化          | ✅ **本阶段做**（SCRATCHPAD_FORMAT_PROMPT 调用）       |
| SemanticMemory | ① Topic Change（IM+≥4轮）         | ✅ **本阶段做**（≥4 轮触发；不限制 IM；CLI/Desktop/WebUI 都覆盖） |
| SemanticMemory | ② 会话结束（双轨提取）             | ✅ **本阶段做**                                          |
| SemanticMemory | ③ 上下文压缩前（Quick Facts 正则） | ✅ **本阶段做**（合并进压缩流程）                  |
| Episode        | 会话结束（LLM + ActionNode）        | ✅ **本阶段做**                                          |

> **关于 ① Scratchpad 即时同步**：OpenAkita 是"先 IntentAnalyzer 分析后再写 scratchpad"——关键条件 `intent != IntentType.CHAT` 时才写，否则闲聊/确认/感谢会污染 current_focus。nanobot 现状无 IntentAnalyzer，因此 Phase 2 **新增轻量级意图识别器**（`nanobot/memory/intent.py`，纯启发式规则，O(10ms) 无 LLM 调用），由它决定 T0 是否真正写入 scratchpad。意图识别器是 T0 路径的前置门（gate），不替代现有 LLM 决策，仅作快速分流。
>
> **关于 ① Topic Change**：OpenAkita 限定 IM 通道是因为 IM 多人对话最易发生话题跳转；但 nanobot 单 agent 主场景下，CLI/Desktop/WebUI 中**用户本身就会频繁切换话题**（一个会话可能上午聊项目 A、下午问项目 B），≥4 轮的 topic_change 检测同样适用。把 IM 限制去掉，所有 ≥4 轮 session 都跑检测。

### 2.2 nanobot 触发点（本阶段采纳）

| 触发点                                                  | 驱动来源                                       | 提取内容                                                              | 时延要求                                |
| ------------------------------------------------------- | ---------------------------------------------- | --------------------------------------------------------------------- | --------------------------------------- |
| **T0**: 每轮对话后即时同步                          | `AgentHook.after_run`                       | scratchpad `current_focus`（系统直写，但仅在 `classify_intent != CHAT` 时触发，见 §6.5） | 同步；写入 < 50ms（含分类 < 10ms） |
| **T1**: 会话结束（`shutdown` / `on_finally`）   | `AgentHook.on_finally`                       | memories + episodes + scratchpad LLM 深度格式化                      | 异步后台；不阻塞 shutdown               |
| **T2**: 用户显式结束会话（DELETE 会话）          | `SessionManager.set_delete_observer`         | memories + episodes + scratchpad LLM 深度格式化                      | 异步后台；响应延迟 < 5s                 |
| **T3**: 上下文压缩（compaction）                 | 复用`MemoryArchiver.archive_session` 路径 | Quick Facts（规则信号）+ 软触发 episode                              | 与压缩同步完成                          |
| **T4**: 异常退出（`on_error`）                 | `AgentHook.on_error`                         | scratchpad 紧急保存（不调 LLM；只覆盖 current_focus）              | 同步；防止 current_focus 丢失           |
| **T5**: 话题切换检测（Topic Change）           | `AgentHook.before_iteration`                 | 检测：会话 user 消息 ≥ 4 → LLM 判断 CONTINUE/NEW；触发：buffer ≥ 3 轮 → fire-and-forget semantic 提取 | 异步 fire-and-forget；延迟 ≤ 30s        |

> **T0 与 T1/T2 的区别**：
> - T0 是每轮都做的轻量同步——只覆写 `current_focus`，不调 LLM，< 50ms 完成
> - T1/T2 是会话结束的重格式化——调 LLM 读取 episode/action_nodes，重组 scratchpad 四个字段（Markdown 2000 字以内）
>
> **T5 Topic Change 检测规则**（对应 OpenAkita §3.1 时机一）：
> 1. **不限制通道**：CLI / Desktop / WebUI / IM 全部适用
> 2. **检测阈值**：当前 session.messages 中 user 消息数 ≥ 4 时才发起检测（每轮 before_iteration 时累计）
> 3. **检测方法**：调 LLM（轻量 prompt）判断"最近 1 条消息 vs 之前 ≥3 条消息"是否主题相关
> 4. **触发动作**：若话题切换 → 旧 focus 滚入 `active_projects` + fire-and-forget 调用 Extractor 仅做 semantic 提取（不调 episode/scratchpad 避免重复工作） + 清空本会话的 topic-change 缓冲
> 5. **缓冲与阈值分离**：检测阈值 ≥ 4 防误判；提取阈值 buffer ≥ 3 即可（buffer 在第 4 条消息到达时通常已累积 ≥ 3 轮）
>
> **不做的触发**：暂无——七个触发点 Phase 2 全部覆盖。

## 三、混合提取架构

### 3.1 提取流水线

Phase 2 核心是 `MemoryExtractor` 类，串起 4 个阶段：

```
┌──────────────────────────────────────────────────────────────────┐
│                  MemoryExtractor.extract_session                  │
└──────────────────────────────────────────────────────────────────┘
        │
        ▼
┌────────────────────────┐
│ 阶段 1: 系统提取         │  (无需 LLM；纯结构化解析)
│  ├ ActionNode 捕获       │

│  └ scratchpad 当前值快照  │
└────────────────────────┘

┌────────────────────────┐

│  ┌─ 2a: SEMANTIC_PROMPT ─┐

│  │  输出 Markdown 四段:   │
```

### 3.2 关键决策：三次并发 LLM 调用（语义 + 情节 + scratchpad 独立 prompt）

OpenAkita 在 session_end 调三次 LLM（`EXTRACTION_PROMPT_V2` 用户画像 + `EXPERIENCE_EXTRACTION_PROMPT` 任务经验 + `update_scratchpad` 深度格式化）。Phase 2 采用**三次并发 LLM 调用 + 各自专门 prompt**：

| 调用 | Prompt 常量 | 输出 | 频率 |
|---|---|---|---|
| **语义调用 2a** | `SEMANTIC_EXTRACTION_PROMPT` | `memories[]` + `experiences[]` | 每个 session_end 一次 |
| **情节调用 2b** | `EPISODE_EXTRACTION_PROMPT` | `episode.summary/goal/outcome/...` | 每个 session_end 一次 |
| **scratchpad 调用 2c** | `SCRATCHPAD_FORMAT_PROMPT` | Markdown 四段重组 | 每个 session_end 一次 |

**为什么全部并发**：三个 LLM 调用无相互依赖（2c 用 action_nodes + 当前 scratchpad，不依赖 2b 输出），并发执行把总延迟控制在 ~max(2a, 2b, 2c) ≈ 2-4s（vs 串行 6-12s）。

**为什么独立 prompt 而非合并**：
- **职责清晰**：每个 prompt 可独立优化、独立测试、独立替换
- **失败隔离**：一个调用失败不影响其他；scratchpad 失败时 memories/episode 仍能写出
- **可演进**：未来若要换不同模型跑不同任务（如用小模型做 scratchpad、大模型做 semantic），独立 prompt 是前提
- **对应调研文档**：严格对齐 OpenAkita §三 双轨机制 + §二.2 scratchpad 深度格式化，认知负担最小

**弥补一致性的方法**：三个 prompt 都要求 LLM 对同一对话给出独立判断，并在持久化前由系统去重（精确哈希 + N-Gram）兜底。

### 3.3 Episode 提取的特殊路径

根据 [`../记忆类型论述.md`](../记忆类型论述.md)：

> 孤立的事实会丢失关键上下文。"用户想运行测试" vs "用户在修复 bug 时习惯先跑单元测试"——前者是事实，后者是故事。

Episode 是"故事"，不能靠纯事实拼接，必须保留决策链。Phase 2 的 Episode 提取路径：

1. **不依赖** `MemoryArchiver` 的 Dream 总结（那是 Markdown 链路）
2. **直接读** `session.messages`，构造 `(user_msg, assistant_responses, tool_calls, tool_results)` 序列
3. **调 LLM** 使用专用 `EPISODE_EXTRACTION_PROMPT`，产出 `goal / outcome / summary / entities / tools_used`
4. **系统侧**独立抓 `tool_calls` → `ActionNode` 列表（不需要 LLM），与 LLM 产出的 summary 合并写入 `episodes.action_nodes`
5. **LLM 调用失败时**：跳过 summary 写入，**仅写 ActionNode 列表**（system-driven 兜底），summary 留空 — 仍保留任务故事的结构

> 这样确保即使 LLM 提取失败，**ActionNode 永远能写出**（对应调研文档 §四"系统提取（兜底）"原则）。

## 四、LLM 提示词设计

按调研文档 §三 的三层记忆机制，本阶段交付**三个独立 LLM 提示词**常量，每个 prompt 专门服务一种记忆类型。三个常量集中存放在 `nanobot/memory/prompts.py`，便于单测断言稳定性、未来通过配置覆盖。

### 4.1 `SEMANTIC_EXTRACTION_PROMPT`（语义记忆提取）

服务 `memories` 表写入，合并用户画像 + 任务经验双轨（对应 OpenAkita §3.2 的 Track 1 + Track 2）。

```
你是 AI agent 的语义记忆提取器。从对话中提取值得长期记住的事实。

## 核心原则：分层记录

- 用户画像（user_profile）：记录"用户是谁"——身份、偏好、行为规则、技术环境。
  判断方法：问"一个月后新对话还有用吗？" → 有用 = 记录。
  type 取值：FACT / PREFERENCE / RULE / SKILL / ERROR
- 任务经验（task_experience）：记录"可复用的操作方法或踩坑教训"——
  成功的具体配置、失败的错误信息、错误→修复的完整路径。
  type 取值：EXPERIENCE / SKILL / ERROR
  注意：EXPERIENCE 与用户画像的 SKILL 区分——SKILL 是用户会的能力，EXPERIENCE 是操作经验。

## priority 字段（决定记忆存多久）

- `long_term`（默认）：身份、长期偏好、行为规则、技术栈、踩坑教训——这些跨月跨年仍有用
- `short_term`：临时性上下文、当前项目特定、有明确期限（如"这周要重构 X 模块"）

判断方法：问"3 个月后还有用吗？" → 有用 = long_term；只在这段时间内相关 = short_term。

## 严格区分

- 用户画像 ≠ 任务请求："用户喜欢简洁风格"（画像）vs"用户希望生成 Word 报告"（任务请求，不记录）
- 任务经验 ≠ 普通流水账："用 pytest --tb=short 显示完整错误"（经验）vs"测试通过了"（流水账）
- 用户事实 ≠ AI 推断："用户操作系统为 Windows"（事实）vs"用户应该升级到 Windows 11"（AI 推断）

## 不要记录

- 一次性任务请求："下载X""搜索Y""帮我做Z"
- 任务产物细节：文件大小、下载链接、具体报告内容
- 打招呼、寒暄、确认、感谢
- 系统状态、错误堆栈、调试信息（除非揭示可复用规律）
- AI 的回复内容、任务完成报告

## 输出 JSON

{
  "memories": [
    {
      "track": "user_profile",
      "type": "FACT|PREFERENCE|RULE|SKILL|ERROR",
      "subject": "实体主语（谁/什么）",
      "predicate": "属性/关系（偏好/版本/位于/...）",
      "content": "精炼描述（不照抄原文）",
      "priority": "long_term|short_term",
      "importance": 0.5-1.0,
      "tags": ["tag1", "tag2"]
    }
  ],
  "experiences": [
    {
      "track": "task_experience",
      "type": "EXPERIENCE|SKILL|ERROR",
      "subject": "主题（什么任务/什么操作）",
      "predicate": "属性（成功方法/失败原因/踩坑教训/最终配置）",
      "content": "详细描述（必须含具体参数/路径/错误信息，确保下次可直接复用）",
      "priority": "long_term|short_term",
      "importance": 0.5-1.0,
      "tags": ["tag1"]
    }
  ]
}

如无任何值得记录的内容，对应字段输出空数组。

## 对话内容

{session_messages_json}

## 阶段1 系统提取结果（参考用，可忽略）

- 工具调用摘要: {action_nodes_summary}
- 规则信号命中: {rule_signal_hits}
```

### 4.2 `EPISODE_EXTRACTION_PROMPT`（情节记忆提取）

服务 `episodes` 表写入，对应 OpenAkita §四 的 episode 生成 prompt。

```
基于以下对话轮次，生成一个情节摘要（保留完整的决策链）。
```

## 五、防污染机制设计

### 5.1 污染来源分类

| 污染类型                         | 例子                                                        | 风险     |
| -------------------------------- | ----------------------------------------------------------- | -------- |
| **一次性任务伪装长期偏好** | "用户希望生成苹果照片"（任务）→ "用户喜欢苹果"（错误画像） | 长期污染 |
| **AI 自答当用户偏好**      | "我建议用户使用 X" → "用户偏好 X"                          | 信任崩塌 |
| **任务产物当长期事实**     | "下载链接是 https://..."                                    | 噪声累积 |
| **重复条目堆积**           | "用户用 Windows" 出现 50 次                                 | 检索降级 |
| **高度相似变体**           | "用户喜欢 Python" + "用户偏好 Python" + "用户首选 Python"   | 重复占用 |

### 5.2 三道防线

#### 防线 1：Prompt 层（最弱但成本最低）

§4.1 SEMANTIC_EXTRACTION_PROMPT 中已明示"不要记录"清单和"严格区分"段落。这是软约束，依赖 LLM 服从性。§4.2 EPISODE_EXTRACTION_PROMPT 同样通过"保留决策链"指令防止流水账化。

#### 防线 2：正则拦截层（中等强度，确定性）

```python
# nanobot/memory/filters.py

_TASK_INDICATORS = [
    r"(?:帮我|请帮我|能否帮我)\s*(?:做|写|找|查|搜|生成|创建|打开|下载)",
    r"(?:搜索|查找|查询)\s*[^\s]{1,30}",
    r"(?:生成|创建|制作)\s*[^\s]{1,30}",
    r"(?:下载|上传|保存)\s*[^\s]{1,30}",
    r"(?:整理|清理|删除|移动)\s*[^\s]{1,30}",
    r"(?:帮我看|帮我改|帮我修|帮我测试)",
    r"^(?:可以|能不能|可否|想|要|希望|需要)\s*(?:帮|做|写|找)",
]

_AI_SELF_TALK = [
    r"^我(?:建议|认为|觉得|发现|观察到|注意到)",
    r"^作为\s*AI",
    r"^根据(?:我的|以上)分析",
]
```

任何 `content` 命中 `TASK_INDICATORS` **且** `type` 是 `PREFERENCE`/`FACT` → 拦截并降级为 `task_experience` 类型或丢弃。
任何 `content` 命中 `AI_SELF_TALK` → 直接丢弃。

#### 防线 3：去重层（强约束，确定性）

```
L1: 精确哈希去重
    └ content + subject + predicate 的 SHA256
    └ 命中已有记录 → skip

L2: N-Gram 相似度去重（字符级 3-gram）
    └ 新条目 vs 同类型已有记录
    └ 相似度 > 0.8 → skip（高度重复）
    └ 相似度 ∈ (0.3, 0.8] → 标记为 "candidate_merge"，由 Extractor 决定
       （Phase 2 不调 LLM 二次判定；标记后让后续检索的 BM25 自然去重）
```

### 5.3 与 OpenAkita 的差异

OpenAkita 的 L2 在 30%-80% 区间**调轻量 LLM 二次判定**。Phase 2 改为：

| OpenAkita       | Phase 2             | 理由                                   |
| --------------- | ------------------- | -------------------------------------- |
| 调 LLM 二次判定 | 仅标记，不判定      | 节省 LLM 成本；BM25 已经能处理近似重复 |
| 字符 N-Gram     | 字符 N-Gram（相同） | 算法一致                               |

### 5.4 过滤器实现模块

`nanobot/memory/filters.py` 暴露 3 个公开函数 + 1 个 dataclass：

```python
def is_task_artifact(content: str) -> bool: ...
def is_ai_self_talk(content: str) -> bool: ...
def compute_content_hash(content: str, subject: str, predicate: str) -> str: ...
def ngram_similarity(a: str, b: str, n: int = 3) -> float: ...

@dataclass
class FilterResult:
    keep: bool
    reason: str  # "ok" | "task_artifact" | "ai_self_talk" | "exact_duplicate" | "high_similarity"
    merged_with: str | None = None  # 高相似时指向已有 memory id
```

## 六、scratchpad 处理

scratchpad 是三层记忆中**唯一每轮都更新**的层，因此 Phase 2 实现两种写入路径：

| 路径 | 时机 | 驱动 | 用途 |
|---|---|---|---|
| **T0 即时同步** | 每轮 after_run | 系统直写 | 保持 current_focus 与最新用户消息同步 |
| **T1/T2 LLM 深度格式化** | session_end / 会话删除 | 调 LLM | 重组成结构化 Markdown，便利后续检索/注入 |

### 6.1 scratchpad 的本质（来自 `../记忆类型论述.md`）

> 类比：办公桌便签。当前正在做的事、进行的项目、未解决的问题、下一步计划。

scratchpad 与 memories/episodes 的关键区别：

| 维度     | scratchpad           | memories            | episodes         |
| -------- | -------------------- | ------------------- | ---------------- |
| 写入频率 | **每轮对话**           | 很少变化            | 会话结束时       |
| LLM 介入 | T0 不调 / T1 调       | 必须（语义提取）    | 必须（叙事总结） |
| 写入策略 | UPSERT（整体替换）   | INSERT（追加+去重） | INSERT（追加）   |

### 6.2 两种写入策略（不冲突）

**T0 即时同步路径**（不调 LLM）：
- 触发：每轮 `AgentHook.after_run`
- 写入：`scratchpad.current_focus = 最近 user message[:200]`
- 旧 focus 自动滚入 `active_projects`（最多 5 条，带日期前缀）
- 同步执行，< 50ms 完成
- 目的：让"当前焦点"实时跟用户话题，不等会话结束

**T1/T2 LLM 深度格式化路径**（调 LLM）：
- 触发：`AgentHook.on_finally` / `SessionManager.delete_observer`
- 输入：`current_scratchpad` + `action_nodes_summary`
- 调用：`SCRATCHPAD_FORMAT_PROMPT`（见 §4.3）
- 输出：Markdown 四段（## 当前项目 / ## 近期进展 / ## 未解决的问题 / ## 下一步）
- 解析后整体 UPSERT 到 `scratchpad.content` 字段
- 异步执行（5s 超时）

**为什么不冲突**：
- T0 只动 `current_focus` 一个字段；其他三个字段（active_projects / open_questions / next_steps）由 T1 LLM 整理
- T0 写入频率高（每轮）但代价小；T1 写入频率低（会话结束）但代价大
- T0 在前（每轮），T1 在后（会话结束），后者覆盖前者产生的中间态

### 6.3 scratchpad 完整写入路径

| 触发                       | 路径 | 字段                                              | 写入方式                                                    |
| -------------------------- | ---- | ------------------------------------------------- | ----------------------------------------------------------- |
| `AgentHook.after_run`      | T0   | `current_focus = 最近 user message[:200]`     | 系统直写                                                    |
| `AgentHook.after_run`      | T0   | `active_projects` 增量                          | 若 `current_focus` 变化 → 旧 focus 入栈                  |
| `AgentHook.on_error`       | T0'  | 紧急保存 `current_focus`                        | 同步直写（即使 T0 失败也要保住焦点）                        |
| `AgentHook.on_finally`     | T1   | 全字段（content + 四个结构字段）                  | LLM 调 `SCRATCHPAD_FORMAT_PROMPT` → 解析 Markdown → UPSERT |
| `SessionManager.delete_session` | T2 | 同 T1                                            | 同 T1                                                       |

### 6.4 与现有 `runtime_control.__scratchpad` 的关系

`nanobot/agent/tools/runtime_control.py` 有一个进程内 `__scratchpad: dict[str, JsonValue]`，是 Agent LLM 调用 `set_scratchpad` 工具时使用的。

**两者完全独立**：

- `runtime_control.__scratchpad`：进程级，键值对，给当前 Agent 进程用（self 工具的存储后端）
- SQLite `scratchpad` 表：持久化，结构化（Markdown + 四个列表字段），跨进程共享

未来可让 runtime_control 在 `set_scratchpad` 时同步写入 SQLite；本阶段**不接**这条路径，避免改动范围爆炸。

### 6.5 T0 前置门：轻量级意图识别器

OpenAkita 的 IntentAnalyzer 把意图分为 5 类（chat/query/task/follow_up/command），关键 gate 是 `intent != CHAT` 才写 scratchpad。nanobot 无 IntentAnalyzer，因此 Phase 2 新增 `nanobot/memory/intent.py` 提供纯启发式 `classify_intent()`。

#### 6.5.1 意图类型与 T0 行为

| IntentType | 例子 | T0 是否写 scratchpad | 理由 |
|---|---|---|---|
| **CHAT** | "你好"/"谢谢"/"ok"/"哈哈" | ❌ 不写 | 闲聊不污染 current_focus |
| **QUERY** | "X 是什么"/"为什么 Y" | ✅ 写（标记纯问询）| 用户的关注点值得记录 |
| **TASK** | "帮我实现 X"/"修复 bug" | ✅ 写 | 任务焦点 |
| **FOLLOW_UP** | "继续上次"/"那这个呢" | ✅ 写 | 继续前文焦点 |
| **COMMAND** | "/run pytest"/"请停止" | ✅ 写 | 明确指令 |

#### 6.5.2 启发式规则（无 LLM 调用）

```python
# nanobot/memory/intent.py

from enum import Enum

class IntentType(str, Enum):
    CHAT = "chat"
    QUERY = "query"
    TASK = "task"
    FOLLOW_UP = "follow_up"
    COMMAND = "command"

_GREETING_PATTERNS = [
    r"^(?:你好|hello|hi|hey|嗨|早上好|晚上好|下午好)",
    r"^(?:谢谢|thank|thanks|thx|多谢|感谢)",
    r"^(?:再见|bye|goodbye|拜拜)",
    r"^(?:ok|好的|收到|嗯|哦|哦哦|了解|知道了)",
    r"^(?:哈哈|呵呵|嘿嘿|lol|😂|👍)",
    r"^[!?。.,，]+$",  # 纯标点
]

_TASK_VERBS = [
    r"(?:帮我|请帮我|能否帮我|麻烦)",
    r"(?:实现|写|创建|生成|制作|开发|调试|修复|重构|优化|测试|部署|配置)",
    r"(?:搜索|查找|查询|找|搜|看看)",
    r"(?:打开|关闭|启动|停止|运行|执行|跑|调用)",
    r"(?:删除|移动|重命名|复制|粘贴)",
    r"(?:下载|上传|保存|另存|导出)",
]

_COMMAND_PATTERNS = [
    r"^(?:请|pls|please)\s",
    r"^/\w+",                          # slash command
    r"^(?:给我|给我们)\s",
]

_FOLLOW_UP_MARKERS = [
    r"(?:那个|这个|它|这个方法|上面那个|你之前|上次|刚才)",
    r"^(?:那|这|那这|那这个)\s",
    r"^(?:继续|接着|然后呢|还有呢|还有什么|再来一次)",
    r"\?$|^？$",                       # 追问多为问号结尾
]

def classify_intent(message: str) -> IntentType:
    """Lightweight heuristic intent classifier. ~5ms, no LLM call."""
    text = message.strip()
    if not text or len(text) < 2:
        return IntentType.CHAT

    # 优先级 1: 闲聊/确认（短消息优先匹配）
    for pattern in _GREETING_PATTERNS:
        if re.search(pattern, text, re.IGNORECASE):
            return IntentType.CHAT

    # 优先级 2: 追问标记（依赖上下文的引用）
    for pattern in _FOLLOW_UP_MARKERS:
        if re.search(pattern, text):
            return IntentType.FOLLOW_UP

    # 优先级 3: 明确指令
    for pattern in _COMMAND_PATTERNS:
        if re.search(pattern, text, re.IGNORECASE):
            return IntentType.COMMAND

    # 优先级 4: 任务动词
    for pattern in _TASK_VERBS:
        if re.search(pattern, text):
            return IntentType.TASK

    # 优先级 5: 问号结尾（无任务动词的问句）
    if text.rstrip().endswith(("?", "？")):
        return IntentType.QUERY

    # 优先级 6: 短消息无信号 → 闲聊
    if len(text) < 10:
        return IntentType.CHAT

    # 默认: 假定是任务
    return IntentType.TASK
```

#### 6.5.3 T0 与意图识别器的集成

```python
# nanobot/agent/hooks/memory_extraction.py

async def after_run(self, context):
    msg = _last_user_message(context.session)
    if not msg:
        return

    intent = classify_intent(msg)          # O(5ms), 纯规则
    if intent == IntentType.CHAT:
        # 闲聊不写 scratchpad，避免覆盖任务焦点
        logger.debug("T0 skip: chat intent for {}", context.session.key)
        return

    # QUERY / TASK / FOLLOW_UP / COMMAND → 触发 T0 写入
    new_focus = msg[:200]
    await self.scratchpad_writer.update_focus(context.session.key, new_focus)
```

#### 6.5.4 与全量 LLM IntentAnalyzer 的差异

| 维度 | OpenAkita IntentAnalyzer | Phase 2 启发式分类器 |
|---|---|---|
| 驱动 | LLM 调用（每次消息都跑） | 纯正则匹配（O(5ms)） |
| 准确度 | 高（语义级理解） | 中（句式级启发） |
| 延迟 | 200-500ms | < 10ms |
| 成本 | 每次消息 1 次 LLM 调用 | 0 调用 |
| 误判 | 低 | 边界情况（如反问"你能帮我看下 X 吗"） |

**为什么不上 LLM 分类器**：T0 每轮都跑，加 LLM 等于每轮 +1 调用 → 用户对话成本翻倍；启发式分类器虽然不完美，但 CHAT vs 非 CHAT 的二元判断在正则层面足够准（闲聊/确认/感谢 vs 任务/追问/指令的句式差异明显）。

**失败兜底**：当启发式分类不确定（中等长度消息无信号）→ 默认归类为 TASK（最保守，避免漏写）。后续 Phase 3 可考虑用嵌入相似度 + 历史上下文做"增强分类"。

```python
    ) -> ExtractionResult:
        """主入口：执行完整 4 阶段提取，返回写入统计。"""

    def _system_extract(self, session: Session) -> SystemExtractionResult:
        """阶段1：系统提取 ActionNode + 规则信号。"""

    async def _llm_extract(
        self,
        session: Session,
        system: SystemExtractionResult,
    ) -> LLMExtractionResult:
        """阶段2：并发调用两个 LLM（SEMANTIC + EPISODE），合并返回结果。"""

    def _apply_filters(
        self,
        llm_result: LLMExtractionResult,
        existing_memories: list[Memory],
    ) -> FilteredExtractionResult:
        """阶段3：去重 + 防污染。"""

    def _persist(
        self,
        filtered: FilteredExtractionResult,
        session: Session,
        source: str,
    ) -> PersistenceResult:
        """阶段4：写入 SQLite。"""
```

### 7.5 与 MemoryArchiver 的关系

`MemoryArchiver` 是 Markdown 链路（history.jsonl）的归档器，**不修改**。
Phase 2 的 `MemoryExtractor` 是 SQLite 链路的提取器，**不调用 MemoryArchiver**。

两者唯一的耦合点：`MemoryArchiver.archive_session` 完成后（ContextCompactionEvent succeeded）→ AgentHook.after_run → Extractor 提取。这样保证：

- Markdown 链路：Dream / MEMORY.md 流程不动
- SQLite 链路：在 Dream 完成的同一个时间点触发，但读 session.messages 直接提取

### 8.2 priority 字段处理细则

| 来源 | 何时为 `short_term` | 何时为 `long_term` |
|---|---|---|
| 用户画像 FACT/PREFERENCE/RULE | 临时偏好（"这周想试 X"） | 身份/长期偏好/行为规则 |
| 用户画像 SKILL | — | 全部 long_term（能力是持久的） |
| 任务经验 EXPERIENCE/SKILL | 当前项目特定操作（"本项目用 uv"） | 通用踩坑教训（"pytest 失败先看依赖"） |
| 任务经验 ERROR | — | 全部 long_term（错误教训不能忘） |

**LLM 未输出 priority 时的兜底**：`MemoryExtractor._persist()` 在解析 JSON 时若 priority 字段缺失或非法，按以下规则：

1. type == ERROR → 强制 long_term
2. content 含时间关键词（"今天/这周/本月/暂时/先"） → short_term
3. 其余 → long_term（数据库默认值）

### 8.3 与现有 `nanobot.memory.repository` 的协作

Phase 2 **不修改** `repository.py`，而是通过它已有的 `add_memory` / `add_episode` / `upsert_scratchpad` 写入。新增的提取逻辑全部在 `extractor.py`。

### 8.4 持久化路径（实际 SQL 与方法调用）

`MemoryExtractor._persist()` 把 LLM 输出 + 系统提取结果映射为 dataclass，再调用 `nanobot.memory.repository` 的公开 API，最终生成 SQL。

#### 8.4.1 伪代码

```python
# nanobot/memory/extractor.py

def _persist(
    self,
    filtered: FilteredExtractionResult,
    session: Session,
    source: str,
) -> PersistenceResult:
    now = _now_iso()
    saved_memory_ids: list[str] = []
    saved_episode_ids: list[str] = []

    with self.database.connect() as conn:
        # 阶段 4a: 写入 memories（先写，拿到 ID 供 episode 反向引用）
        for mem in filtered.memories:
            memory_id = str(uuid4())
            memory = Memory(
                id=memory_id,
                content=mem.content,
                type=MemoryType(mem.type),
                priority=_resolve_priority(mem),  # 见 §8.2 兜底
                source="extraction",
                importance_score=mem.importance,
                tags=mem.tags,
                subject=mem.subject,
                predicate=mem.predicate,
                workspace_id=self.workspace_id,
                user_id=self.user_id,
                created_at=now,
                updated_at=now,
            )
            add_memory(conn, memory)              # ← 调 repository.add_memory
            saved_memory_ids.append(memory_id)

        # 阶段 4b: 反向关联（subject == entity 匹配）
        memory_by_subject = {m.subject: m.id for m in filtered.memories}
        linked_ids = [
            memory_by_subject[e]
            for e in (filtered.episode.entities or [])
            if e in memory_by_subject
        ]

        # 阶段 4c: 写入 episode（即使 LLM 失败也写，仅 action_nodes）
        if filtered.episode is not None or filtered.action_nodes:
            episode_id = str(uuid4())
            outcome = (
                EpisodeOutcome(filtered.episode.outcome)
                if filtered.episode and filtered.episode.outcome
                else EpisodeOutcome.COMPLETED
            )
            episode = Episode(
                id=episode_id,
                session_id=session.key,
                summary=filtered.episode.summary if filtered.episode else "",
                goal=filtered.episode.goal if filtered.episode else "",
                outcome=outcome,
                source=EpisodeSource(source),
                action_nodes=filtered.action_nodes,
                entities=filtered.episode.entities if filtered.episode else [],
                tools_used=filtered.episode.tools_used if filtered.episode else [],
                linked_memory_ids=linked_ids,
                started_at=session.created_at,
                ended_at=now,
            )
            add_episode(conn, episode)              # ← 调 repository.add_episode
            saved_episode_ids.append(episode_id)

    return PersistenceResult(
        memory_ids=saved_memory_ids,
        episode_ids=saved_episode_ids,
    )
```

#### 8.4.3 写入失败处理

| 失败类型 | 处理 |
|---|---|
| 单条 memory INSERT 失败（约束冲突） | 跳过该条，记录 warning，继续其余条目；不抛异常 |
| episode INSERT 失败 | 已写入的 memory **不回滚**（SQLite 没有跨事务保护）；记录 error |
| scratchpad UPSERT 失败 | 不抛异常；下次 after_run 重试时仍会覆盖 |
| 整个连接异常 | `with db.connect()` context manager 自动回滚未 commit 的写入 |

### 8.5 linked_memory_ids 反向关联

Episode 与 memories 的关联通过两阶段建立：

1. **写入顺序**：先写 memories（拿到 ID），再写 episode（带 linked_memory_ids）
2. **关联策略**：本期采用 `subject == episode.entities[i]` 模糊匹配
   - 例：episode.entities = ["tests/test_x.py"]，memory.subject = "tests/test_x.py" → 关联
3. **不依赖 LLM 判定**：降低 LLM 成本；Phase 3 再做精细化（按实体提及频次等）

## 九、错误处理与并发

### 9.1 错误隔离原则

| 错误源                      | 处理策略                                                                               |
| --------------------------- | -------------------------------------------------------------------------------------- |
| LLM 提取失败（超时/解析错） | 记录 warning，episode 走系统兜底（首条消息 + ActionNode）写入；memories 跳过；不抛异常 |
| LLM 输出非法 JSON           | 尝试解析为 partial JSON；解析失败 → 跳过本次 memories 提取                            |
| SQLite 写入失败             | 记录 error，已写入条目不回滚（SQLite 没有跨表事务保护）                                |
| Hook 自身抛异常             | `AgentHook._for_each_hook_safe` 已隔离；Extractor 失败不影响主循环                   |

### 9.2 并发模型

```
用户触发 on_finally
    │
    ▼
MemoryExtractionHook.on_finally()
    │
    ├─ 创建 asyncio.Task(extractor.extract_session(...))
    │   └─ 此 Task 与 Agent 主循环独立
    │
    ├─ await asyncio.wait_for(task, timeout=5.0)
    │   │
    │   ├─ 5s 内完成 → 正常退出
    │   └─ 超时 → task.cancel()，记录 warning
    │
    └─ Agent 退出（不阻塞 shutdown）
```

**不引入持久化任务队列**：Agent 进程退出 → 任务丢失。这是已知妥协——如果 Agent 在 extraction 5s 超时窗内崩溃，对应会话的提取会丢。Phase 3 引入持久化队列（基于 history.jsonl 的 cursor 增量 + 启动时回放）解决。

### 9.3 多 Agent 实例

nanobot 当前主要为单 Agent 实例，但 WebUI 可有多个并发会话。每个会话独立创建 `MemoryExtractor` 实例，共享同一个 `MemoryDatabase`（SQLite 已用 `threading.Lock` 串行化）。

### Task 12: 话题切换检测（Topic Change，T5 路径）

**Files**:

- Modify: `nanobot/agent/hooks/memory_extraction.py`
- Test: `tests/memory/test_topic_change.py`

**核心逻辑**：

- 在 `MemoryExtractionHook.before_iteration` 中检查 session.messages 的 user 消息数
- 若 ≥ 4，把"最近 1 条 user message"与"之前 ≥3 条 user message"打包，调轻量 LLM 判断 CONTINUE 或 NEW
- LLM 命中 NEW 时：
  1. 旧 scratchpad.current_focus 滚入 active_projects
  2. fire-and-forget 创建 asyncio task，调 `Extractor.extract_topic_change(buffer)` —— **仅做 semantic 提取**（不调 episode/scratchpad LLM，避免重复工作）
  3. 清空 session._topic_change_buffer

**测试用例**：

- 给定 4 条 user 消息（话题连续）→ LLM 返回 CONTINUE → 不触发提取
- 给定 4 条 user 消息（话题 1-3 一类，4 跳到另一类）→ LLM 返回 NEW → 触发 semantic 提取
- 给定 3 条 user 消息 → 跳过检测（未达阈值）
- LLM 调用失败 → 记录 warning，按 CONTINUE 处理（不丢失后续对话机会）
- fire-and-forget task 不阻塞主循环：await asyncio.wait_for(timeout=0.5s) 必须立即返回

**专用 prompt**（新增 `prompts.py` 常量 `TOPIC_CHANGE_DETECTION_PROMPT`）：

```
判断"最新消息"与"近期对话"是否同一主题。

近期对话（最多 4 条，按时间正序）：
{recent_messages}

最新消息：
{latest_message}

回答 JSON：{"same_topic": true|false, "reason": "一句话说明"}
```

**提交**：`feat(memory): add topic change detection with LLM-based semantic boundary`

### Task 13: scratchpad LLM 深度格式化（T1/T2 路径）

**Files**:

- Modify: `nanobot/memory/extractor.py`
- Modify: `nanobot/memory/prompts.py`（已定义 `SCRATCHPAD_FORMAT_PROMPT`，本 Task 添加调用逻辑）
- Test: `tests/memory/test_scratchpad_format.py`

**核心逻辑**：

- `MemoryExtractor._format_scratchpad(current_scratchpad, action_nodes)` 调 `SCRATCHPAD_FORMAT_PROMPT`
- 解析 LLM 输出的 Markdown 四段（## 当前项目 / ## 近期进展 / ## 未解决的问题 / ## 下一步）
- 把四段解析为结构化字段（`active_projects` 列表 / `current_focus` 字符串 / `open_questions` 列表 / `next_steps` 列表）
- 调 `repository.upsert_scratchpad()` 写入
- 失败兜底：LLM 输出非 Markdown / 超 2000 字 / 解析失败 → 用系统直写路径覆写 scratchpad（保留当前 current_focus + active_projects 滚动），不抛异常

- LLM 输出非 Markdown（纯文本）→ 走系统兜底，不抛异常
- LLM 调用超时 → 走系统兜底，current_focus 不丢
- Markdown 四段解析：缺 ## 当前项目 → 该字段为空列表，不报错

**提交**：`feat(memory): add LLM-driven scratchpad deep formatting at session end`

## 十二、风险与缓解

| 风险                             | 影响              | 缓解措施                                                                  |
| -------------------------------- | ----------------- | ------------------------------------------------------------------------- |
| LLM 提取成本高                   | 用户付费增加      | 默认 disable，opt-in 启用；批量任务中限速 1 次/分钟                       |
| LLM 输出幻觉污染                 | memories 错误内容 | 三道防线（prompt + 正则 + 去重）；定期 review 接口                        |
| SQLite 单文件锁竞争              | 写入延迟          | `threading.Lock` 串行化已足够；LLM 调用本身是异步，不阻塞其他 SQLite 读 |
| Agent 进程崩溃导致 5s 内提取丢失 | 数据丢失          | 已知妥协；Phase 3 引入持久化队列                                          |
| Memories 表快速膨胀              | 检索性能下降      | Phase 3 引入 decay 机制 + 重要度衰减                                      |
| 既有 MemoryStore 测试受影响      | Phase 2 失败      | MemoryExtractor 与 MemoryStore 零耦合，独立测试                           |
